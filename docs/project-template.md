# Project title

## Status

Use exactly one status: `planned`, `in progress`, `locally verified`, or `public demo`.

## Problem

Describe the user, the operational problem, and the input/output boundary.

## Why it matters

Explain the business or engineering value and the simplest useful baseline.

## Architecture

Show the data flow, service boundaries, dependencies, and failure paths.

## Data and privacy

Document data provenance, license, synthetic/public fixture rules, retention, and redaction boundaries.

## Evaluation

Name the dataset, metrics, baseline, command, artifact, and known limitations. Every metric needs reproducible evidence.

## Security and failure modes

Describe untrusted inputs, secrets, permissions, abuse cases, timeouts, retries, safe refusal, and logging boundaries.

## Local quick start

Give exact commands that work without undisclosed credentials.

## Evidence

Link tests, traces, screenshots, benchmark output, or deployment logs. Separate design, local verification, and public deployment.

## Cost and latency

State what is measured, what is estimated, and which provider/model assumptions affect the result.

## What is not implemented

List missing integrations, unavailable production guarantees, and intentionally simulated components.

## Next improvement

Choose the next change from a measured failure or a clearly stated user need.
